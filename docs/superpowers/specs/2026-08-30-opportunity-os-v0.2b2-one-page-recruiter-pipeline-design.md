# Opportunity OS V0.2B2 — One-Page Recruiter CV Pipeline

Date: 2026-08-30
Status: review-required
Base: `main` at `8b1de63037f03a2dfb65cf0d400a787211bd4094`
Supersedes: V0.2B1 layout ceiling and recruiter-quality acceptance rules where they conflict with this spec.

## 1. Purpose

V0.2B2 makes recruiter-facing CV generation reproducible, one-page, evidence-safe and usable from a fresh chat or operator session without reconstructing prior context from memory.

The feature keeps Opportunity OS as the authority for truth, evidence, track isolation and application state while introducing a dedicated recruiter-facing composition layer and a stricter one-page rendering/quality contract.

Target flow:

```text
Opportunity / RadarAssessment
        ↓
winning CandidateTrack
        ↓
private MasterFacts + EvidenceCatalog
        ↓
EvidenceSelector
        ↓
CVComposer
        ↓
ClaimValidator
        ↓
validated CVDocumentModel
        ↓
RecruiterDocumentComposer
        ↓
RecruiterDocumentValidator
        ↓
RecruiterDocumentModel
        ↓
OnePageRenderer
        ↓
RecruiterQualityQA
        ↓
private one-page PDF
        ↓
ApplicationPacket
```

The operational entrypoint must execute this chain as one command. A chat agent must not hand-assemble intermediate documents as the normal path.

## 2. Incident that motivates V0.2B2

A real Coca-Cola Andina preparation exposed a product gap:

- semantic validation passed;
- the PDF was selectable and ATS-safe at a basic level;
- `LayoutQA` considered the output valid;
- the recruiter-facing result was poor: skills rendered vertically, weak information hierarchy, fragmented experience, and a second page with low value.

This was not a data-quality failure. It was a contract failure between semantic CV composition and recruiter-facing presentation.

V0.2B1 allows up to two pages and treats low utilization as a warning. That behavior is no longer acceptable for the default recruiter-facing profile in Opportunity OS.

## 3. Non-negotiable one-page contract

Recruiter-facing CVs generated by the canonical pipeline MUST contain exactly one PDF page.

```text
page_count == 1
```

Two pages are not a warning and are not an alternate automatic mode. There is no automatic two-page fallback in V0.2B2.

If a valid recruiter-facing document cannot be rendered to one page while preserving the configured minimum typography and content contracts, preparation fails closed with the existing blocked-render family and a bounded error code:

```text
BLOCKED_RENDER
error.code = recruiter_one_page_failed
```

The pipeline must never shrink text below the configured minimum simply to satisfy the page limit.

## 4. Reference standard

The recruiter-facing structure is based on two previously successful real artifacts produced for Maptek and Esri Canada. Their personal content remains private and is not committed, but their structural properties become the canonical benchmark:

```text
NAME
TARGET-SPECIFIC HEADLINE
compact contact metadata

PROFILE
2–3 compact lines

RELEVANT TECHNOLOGY
2–4 categorized compact lines

SELECTED WORK
3–4 target-relevant projects

EXPERIENCE
compact role line + at most one concise evidence-backed bullet per included role

EDUCATION & TRAINING
compact close
```

The benchmark is structural, not semantic. Golden fixtures in the public repository must use fictional candidate data.

## 5. External benchmark research

V0.2B2 adopts patterns, not an entire third-party product.

### 5.1 RenderCV

Reference: https://github.com/rendercv/rendercv
License: MIT

Useful patterns:

- structured YAML/Pydantic source separated from presentation;
- deterministic PDF generation;
- themes kept separate from candidate content;
- machine-readable text layer;
- dedicated ATS proof scripts using independent text extractors and commercial resume parsers;
- agent-oriented repeatable rendering workflow.

Opportunity OS may use RenderCV/Typst as an internal rendering engine or implement a compatible adapter boundary. RenderCV never becomes the semantic authority for candidate claims.

### 5.2 sb2nov/resume

Reference: https://github.com/sb2nov/resume

Useful pattern:

- dense single-page developer resume;
- one-column reading order;
- compact sections without sidebars or graphical skill widgets.

### 5.3 Reactive Resume

Reference: https://github.com/AmruthPillai/Reactive-Resume

Useful pattern:

- domain/schema separated from renderer;
- preview/export parity as an architectural goal.

Opportunity OS does not adopt Reactive Resume as a runtime dependency for V0.2B2.

### 5.4 JSON Resume

Reference: https://github.com/jsonresume

Useful pattern:

- portable structured resume schema;
- renderer/theme independence.

Opportunity OS keeps its stricter provenance-aware internal models rather than replacing them with JSON Resume.

## 6. Architectural boundaries

### 6.1 Semantic authority remains in Opportunity OS

Only these layers may decide whether candidate-specific content is true and usable:

```text
MasterFacts
EvidenceCatalog
EvidenceSelector
CVComposer
ClaimValidator
```

`ClaimValidator` remains the hard semantic gate and runs before any recruiter-specific grouping or layout logic.

The recruiter composer may select, group, order and omit only claims from a `CVDocumentModel` that has already passed `ClaimValidator`. It may not invent facts, infer unsupported target requirements, promote projects to employment, alter dates, create metrics, silently merge tracks, or introduce candidate-specific wording that did not pass semantic validation.

### 6.2 RecruiterDocumentComposer

Introduce a dedicated recruiter-facing composition layer after semantic validation and before rendering.

It is responsible for:

- choosing a validated target-specific headline claim;
- selecting validated summary claims within a strict line/character budget;
- grouping validated skill claims into compact labeled rows;
- choosing a maximum of four target-relevant validated project claims;
- compacting included validated experience claims to a role line plus zero/one approved bullet;
- ordering sections according to the recruiter profile;
- dropping lower-relevance optional validated claims before layout is allowed to reduce typography.

It consumes the validated `CVDocumentModel`, `ValidationResult`, evidence-selection metadata and deterministic recruiter policy. It does not read private MasterFacts/EvidenceCatalog directly and does not render PDF bytes.

### 6.3 RecruiterDocumentValidator

A focused structural validator checks that recruiter composition did not create new candidate-specific semantics.

It must verify at least:

- every candidate-specific visible token resolves to one or more claim IDs from the validated source `CVDocumentModel`;
- every referenced claim ID is in `ValidationResult.validated_claim_ids`;
- candidate-specific token text is identical to an allowed source claim text or a deterministic concatenation of source claim texts with repository-owned separators;
- repository-owned section/group labels are from an allowlisted recruiter policy and do not imply unsupported candidate skills;
- project/experience caps and bullet caps are respected;
- no cross-track or unvalidated claim can enter the recruiter document.

### 6.4 Renderer

The renderer receives only a recruiter document that passed `RecruiterDocumentValidator`.

It is responsible for deterministic one-page typesetting and verified contact/link annotations. It may not rewrite visible candidate-specific text.

### 6.5 RecruiterQualityQA

Quality QA runs after render and before `ApplicationPacket` creation.

It evaluates recruiter-facing structural and PDF properties only. It cannot alter content.

## 7. RecruiterDocumentModel

V0.2B2 adds a presentation-specific structured model rather than forcing the renderer to infer grouping from atomic `CVClaim` rows.

Required conceptual shape:

```text
RecruiterDocumentModel
- document_version
- language
- source_cv_document_version
- identity_claim_id
- headline_claim_id
- contact_claim_ids[]
- profile_claim_ids[]
- technology_groups[]
  - label_id
  - skill_claim_ids[]
- selected_projects[]
  - project_claim_ids[]
- experience_entries[]
  - claim_ids[]
  - bullet_claim_ids[]  # max 1 visible bullet per included role
- education_claim_ids[]
- language_claim_ids[]
- link_claim_ids[]
```

Candidate-specific strings are resolved from validated source claims. The recruiter model primarily carries grouping/order references, not a second independent source of candidate truth.

Grouping metadata such as `Software & Data`, `Operations & Systems`, or `Geospatial` is controlled by repository configuration and is not candidate evidence. A group label must not imply a skill that is absent from its member claims.

## 8. Skill grouping contract

Atomic skill-per-paragraph output is forbidden in the recruiter profile.

Renderer-facing skills must be grouped before rendering.

Example presentation shape:

```text
Software & Data: Python · FastAPI · SQL · PostgreSQL/PostGIS · React · TypeScript
Operations & Systems: workflow automation · inventory · purchasing · process improvement
Geospatial: MapLibre · Leaflet · CesiumJS · QGIS · spatial data
```

Constraints:

- each visible skill token resolves to a validated skill claim;
- default maximum visible groups: 4;
- default maximum visible skill tokens: 24;
- no bars, stars, percentages, rankings or icons;
- ordering is target-relevance first, then stable deterministic fallback order;
- unsupported target requirements remain gaps and are never inserted for keyword matching.

## 9. Content budgets

The recruiter composer owns deterministic content budgets.

Default English/Spanish recruiter profile:

```text
headline:              max 2 rendered lines
profile:               max 3 rendered lines
technology groups:     max 4 groups / 24 skill tokens
selected projects:     max 4
project description:   max 2 rendered lines per project
experience entries:    max 5
experience bullets:    max 1 per included entry
education items:       max 4
pages:                 exactly 1
```

The implementation may use deterministic character/word pre-budgets to reduce render retries, but final acceptance is based on the rendered PDF and QA.

## 10. Deterministic fit strategy

V0.2B2 must not solve overflow by repeatedly shrinking fonts.

The fit order is:

```text
1. select and semantically validate target-relevant evidence/claims
2. compose recruiter document using section/item budgets
3. validate recruiter document references
4. render at fixed recruiter typography
5. if overflow: remove lowest-relevance optional validated claims using deterministic priority rules
6. revalidate recruiter document references
7. re-render
8. if still not exactly one page: BLOCKED_RENDER / recruiter_one_page_failed
```

Items that may be removed first:

1. optional links duplicated elsewhere;
2. lower-relevance skill claims;
3. lower-relevance project #4, then #3 if policy allows at least two projects;
4. lower-relevance experience entries that are not required for truthful chronology/context;
5. optional training claims.

Mandatory identity/contact and policy-required sections may not be silently removed.

The exact reduction sequence must be testable and deterministic.

## 11. Typography and page profile

Default recruiter theme:

```text
page:              A4
columns:           1
minimum body:      9.0 pt
preferred body:    9.4–10.0 pt
name:              17–20 pt
headline:          10.5–12 pt
section labels:    10–11.5 pt bold
metadata:          8.8–9.5 pt
```

One restrained non-semantic accent color is allowed.

Forbidden:

- photos;
- logos;
- sidebars;
- multi-column body layout;
- tables used to fake layout;
- charts;
- skill bars;
- semantic icons;
- rasterized text;
- network fonts/resources.

## 12. Render engine strategy

Preferred implementation boundary:

```text
validated CVDocumentModel
        ↓
RecruiterDocumentComposer
        ↓
validated RecruiterDocumentModel
        ↓
RecruiterRenderer protocol
        ↓
RenderCVTypstAdapter
```

The adapter may map the validated Opportunity OS recruiter document into a private temporary RenderCV-compatible input/theme and invoke the local render engine.

Important constraints:

- the final dependency/toolchain stays inside the `opportunity-os` repository/runtime;
- no second resume repository is created;
- candidate private snapshots remain gitignored;
- generated CVs/ApplicationPackets remain private/generated artifacts;
- no network access is required at render time;
- the adapter cannot bypass either `ClaimValidator` or `RecruiterDocumentValidator`;
- engine failure maps to `BLOCKED_RENDER`.

If dependency feasibility or deterministic packaging makes RenderCV unsuitable, the implementation may retain ReportLab behind the same `RecruiterRenderer` interface, but it must satisfy every recruiter-quality acceptance rule in this spec. The interface must prevent the semantic layer from depending on one renderer implementation.

## 13. RecruiterQualityQA hard gates

`PREPARED` is impossible unless all hard gates pass:

```text
page_count == 1
A4 page size
single canonical reading flow
extractable/selectable text present
body font >= 9.0 pt
headline <= 2 rendered lines
no renderer overflow/clipping
no second/trailing page
no semantic images/logos/charts/tables/skill widgets
skills represented as grouped recruiter rows
project_count <= 4
experience visible bullets <= 1 per included role
all candidate-specific visible tokens resolve to validated source claims
```

A failure maps to `BLOCKED_RENDER` with a bounded code identifying the failed gate.

Warnings may still exist for aesthetics that do not violate the hard recruiter contract, but `page_count != 1` is never a warning.

## 14. ATS verification

V0.2B2 strengthens ATS verification beyond `PyPDF extracted some text`.

CI/public fixtures must include at least two independent local extraction checks when available in the supported environment, for example:

```text
pypdf/PyMuPDF extraction
pdftotext/Poppler extraction
```

For each golden fixture, tests compare extracted output against known fictional ground-truth fields:

- candidate name;
- email;
- phone;
- included role/company strings;
- dates;
- education strings;
- project titles;
- skill tokens.

Commercial ATS parsers are research/periodic validation only and are not required in normal CI because they require external services/credentials.

## 15. Golden recruiter fixtures

Public golden tests use fictional data and must cover at least:

### Fixture A — Software / geospatial

Structural analogue to the successful Esri/Maptek pattern:

- three skill groups;
- four projects;
- five compact experience entries;
- education/training close;
- exactly one page.

### Fixture B — Technology + operations

Covers the cross-domain bridge needed by targets such as Coca-Cola Andina, Stellantis, Holcim and operations-tech employers:

- software/data skills;
- operations/process skills;
- two to four relevant projects;
- real-style operations experience represented separately from software projects;
- unsupported enterprise tools kept as gaps.

Golden tests must assert structural contracts and extraction ground truth, not pixel-perfect private CV snapshots.

## 16. Canonical operator entrypoint

Fresh chats/operators must use one documented command instead of manually rebuilding the pipeline.

Target command contract:

```bash
python -m app.application.prepare \
  --opportunity <opportunity-snapshot.yaml-or-json> \
  --master-facts profile/master_facts.local.yaml \
  --evidence-catalog profile/evidence_catalog.local.yaml \
  --output-root artifacts/applications
```

The command must:

1. load and validate private snapshots;
2. load a real opportunity/radar assessment or build the supported canonical input form;
3. resolve the application track;
4. select evidence;
5. compose canonical `CVDocumentModel`;
6. run `ClaimValidator`;
7. compose recruiter document from validated claims only;
8. run `RecruiterDocumentValidator`;
9. render one-page PDF;
10. run `RecruiterQualityQA`;
11. write an `ApplicationPacket` only when all gates pass;
12. print a concise machine/operator-readable result containing status, application ID, output path, CV hash, packet hash and unresolved gaps.

The command never sends email or submits an ATS form.

## 17. Agent runbook

Create:

```text
docs/OPPORTUNITY_OS_AGENT_RUNBOOK.md
```

The runbook is the canonical entrypoint for a fresh ChatGPT/Codex/operator context.

It must say explicitly:

```text
DO NOT reconstruct CV generation from memory.
DO NOT hand-build recruiter PDFs when the canonical command is available.
PREPARED requires exactly one recruiter-quality page.
PREPARED ≠ APPROVE ≠ SEND.
Private candidate snapshots and generated artifacts never enter the public repo.
```

It includes:

- prerequisites;
- private file locations;
- canonical command;
- expected statuses;
- what to inspect after generation;
- what blocks sending;
- how to handle target-account outreach versus active postings;
- how to report gaps rather than invent requirements.

README and the Vault operational-context note should point future agents to this runbook.

## 19. Dependency and licensing rules

- RenderCV is MIT and may be used as a dependency/reference subject to normal license notices.
- Third-party theme/code copied substantially into Opportunity OS must preserve required license attribution.
- Prefer adapter integration and an Opportunity OS-owned theme/config over copying large third-party codebases.
- Do not add SaaS or paid runtime requirements.
- Normal CV preparation must work offline once dependencies are installed.

## 20. ApplicationPacket semantics

`ApplicationPacket` remains the authority for a successfully prepared application artifact.

V0.2B2 adds recruiter-renderer/document version fields only if needed to make the output reproducible. Existing semantic hashes must continue to change when visible validated candidate content, recruiter grouping/order or renderer semantics change.

A recruiter-quality failure produces no successful packet.

`PREPARED` now means both:

```text
semantic claims valid
AND
recruiter-facing one-page contract valid
```

It does not mean the application is approved or sent.

## 21. Error handling

Bounded error codes must distinguish at least:

```text
recruiter_one_page_failed
recruiter_text_not_extractable
recruiter_body_font_too_small
recruiter_headline_overflow
recruiter_content_overflow
recruiter_render_failed
recruiter_reading_order_failed
recruiter_unvalidated_claim_reference
```

Errors remain under blocked preparation states already understood by the system unless implementation reveals a compelling compatibility reason to add a new public preparation status.

Partial PDFs are removed on hard failure.

## 22. TDD acceptance matrix

Implementation must be test-first.

Required regression cases:

1. existing two-page-valid V0.2B1 fixture becomes RED under recruiter profile;
2. one-page golden software fixture passes;
3. one-page tech+operations fixture passes;
4. atomic skills cannot reach renderer as individual recruiter paragraphs;
5. recruiter composer rejects/unreferences claims not present in the validated source document;
6. more than four selected projects is reduced deterministically or blocked;
7. more than one visible bullet per experience entry is reduced deterministically or blocked;
8. font cannot fall below 9 pt to force a fit;
9. unsupported target skills remain unresolved gaps;
10. renderer receives only a structurally validated recruiter model;
11. fixed semantic input produces deterministic recruiter document ordering;
12. fixed render input produces deterministic output/hash within the supported engine contract;
13. extraction ground truth survives PDF generation;
14. page two causes hard failure and no packet;
15. fresh CLI invocation produces the same result without chat-specific state;
16. agent runbook command matches the executable CLI contract;
17. private/generated-file guard stays green.

## 24. Acceptance criteria

V0.2B2 is complete only when:

1. recruiter-facing canonical CV output is exactly one A4 page;
2. the one-page rule is a hard gate, never a warning;
3. skills render as compact categorized rows, not one paragraph per skill;
4. target-specific headline/profile/projects are selected from semantically validated claims only;
5. projects are capped at four;
6. experience is compact and evidence-backed;
7. typography stays at or above the minimum body font;
8. overflow triggers deterministic content reduction, then fail-closed if still impossible;
9. ATS extraction tests preserve known fictional ground truth;
10. private user facts/evidence remain gitignored;
11. a fresh operator can run one canonical command from the documented runbook;
12. the command creates an `ApplicationPacket` only after semantic and recruiter-quality gates pass;
13. `PREPARED ≠ APPROVE ≠ SEND` remains intact;
14. full unit/integration/release tests pass;
15. compile/static checks and private/generated-file guards pass;
16. a private real smoke test produces a recruiter-quality one-page target CV comparable in structure/density to the successful Maptek/Esri benchmark before any new batch of outreach CVs is prepared.

## 25. Explicitly out of scope

V0.2B2 does not include:

- two-page resumes;
- multiple recruiter themes;
- company branding/logos;
- generative visual design selection;
- browser WYSIWYG resume editor;
- automatic email sending;
- ATS form submission;
- recruiter contact discovery;
- rewriting unsupported requirements into experience;
- automatic scoring-weight learning;
- paid ATS parser APIs in normal CI.

## 26. Final invariant

```text
EVIDENCE DECIDES WHAT WE MAY SAY.
CLAIM VALIDATOR DECIDES WHAT IS SEMANTICALLY SAFE.
RECRUITER COMPOSER DECIDES WHAT VALIDATED CONTENT TO SHOW.
THEME DECIDES HOW IT FITS.
QA DECIDES WHETHER IT IS GOOD ENOUGH TO BECOME PREPARED.

PREPARED == VALID EVIDENCE + VALID CLAIMS + EXACTLY ONE RECRUITER-QUALITY PAGE
PREPARED != APPROVED
PREPARED != SENT
```
